# Code quality review, 2026-10-16

Scope: product code only (`docs/architecture.md`, `src/**`, `patches/brutal/{transform.py,BrutalSource.targets}`, `samples/**`, `tools/**`, READMEs). Read-only review; nothing was built or run. Severity: high = misleads or breaks a developer, medium = real quality or risk, low = polish. Line numbers are from the tree as reviewed. Bare file names are relative to the project named in the section heading.

Note: while this review ran, another change set edited `Profile.cs`, `profiles/*`, the ICD and sample READMEs and `scripts/validate-web-profile.sh` and added `ProfileJsonSyncTests` (API version 1.3, push constants 128, three bound sets, game tier marked as not yet implemented). The first-pass findings on API version, profile-vs-ICD drift and the game tier are therefore dropped; everything below was re-checked against the tree after those edits.

## Summary

1. The code is consistent and well commented; the problems are mostly contracts that disagree with each other, not logic errors.
2. The device contract is now consistent between `Profile.cs`, the profile JSON and the ICD README (1.3, 128 B push constants, 3 sets, with a sync test), but the shader pipeline (`PUSH_MAX_BYTES = 64`), `tools/README.md` and `architecture.md:88` still say 64.
3. `docs/architecture.md` calls itself the single source of truth but is wrong or incomplete in five places (sections 5.1, 6, 7, 12 and the device-creation policy).
4. No document tells a game developer where their code goes, which BRUTAL libraries do not exist in the browser (Vma, ShaderC, Texture/Stb, Concurrency), or which ICD behaviours are performance traps.
5. Experiment scaffolding ("stand-in" mode for exp-03, exp-05 references) is still in the product page, its e2e test, its README and `vite.config.ts`.
6. `HelloMeshApp` is a 250-line monolith (frame loop, swapchain, screenshots, markers, sound); game code also reaches into host concerns through `GraphicsConfig.AllowDeviceWaitIdle`. It is not yet a base to add game logic to.
7. Hot-path helpers build strings before their once-check, so ignored-but-called functions (`vkCmdSetDepthBias`) allocate on every call; the push-constant ring silently wraps after 4096 draws; device loss is logged but never returned as `VK_ERROR_DEVICE_LOST`.
8. Public surface is looser than the stated convention: `CS1591` is suppressed in three projects, test seams are compiled into product classes, `WebGpuBridge` is public but cannot be implemented outside its assembly.
9. Three duplicates will rot: WGSL binding reflection in both JS and C# (the manifest `bindings` array is written and never read), the browser boot script in four places, "find a WebGPU Chromium" in four scripts.
10. Dead code is small and easy to remove: `patchYFlip`, `--include`, `BRUTAL_VULKAN_PLUGGABLE_LOADER`, six unused central package versions (one a prerelease), the `Dll` const in `Glfw.cs`.

## Fix first

1. Write `docs/game-guide.md` (where game code goes, supported Vulkan subset, unavailable BRUTAL libraries, performance rules) and link it from the root README.
2. Finish the device-contract reconciliation: push-constant size in `tools/build-shaders.mjs`, `tools/README.md` and `architecture.md:88` versus the ICD's 128; correct `architecture.md` sections 5.1, 6, 7, 12 and add the device-creation policy.
3. Remove all "stand-in"/experiment code from `HelloMesh.Web` (main.ts, e2e, serve-check, vite.config, README, plugin header) and shrink the Vite plugin.
4. Fix the ICD hot-path and failure behaviour: lazy once-logging in `IcdLog`, push-ring overflow, `VK_ERROR_DEVICE_LOST`, dynamic depth bias.
5. Split `HelloMeshApp` into a reusable render host and a scene with `Update(dt)`/`Record(cmd)`; delete `AllowDeviceWaitIdle`, `GlbReader`, and move screenshot and marker code out of the shared path.
6. Tighten the public surface: drop the `CS1591` suppressions and document, make `WebGpuBridge`/`WebIcd.Bridge` and the wire constants internal, collect test seams in one place.
7. Repair the build entry points: quick-start `dotnet test` line, `npm ci` race, `.spv` inputs and stale-file handling in `Shaders*.targets`, unused package versions, BRUTAL `bin/obj` glob.
8. Replace the four boot scripts and four Chromium-discovery snippets with one shared `boot.js` and one `browser-launch.mjs`.

## Findings

### Contracts and documentation (architecture.md, READMEs, root)

- [severity: high] docs (none exists) — Nothing tells a game developer where to put game code; that `Brutal.Vulkan.Vma`, `Brutal.ShaderC`, `Brutal.Texture`/Stb and `Brutal.Concurrency` are unavailable; that shaders must be precompiled at build time (a SPIR-V hash miss fails `vkCreateShaderModule`); that `vkCmdBlitImage` is missing (no GPU mip generation); that persistently mapped memory is re-uploaded on every submit; that a descriptor write after first bind rebuilds a GPUBindGroup from JSON; that game code runs on the Mono interpreter; that an exception in the frame delegate ends the loop for good; or that forgetting `WebIcd.Install()` shows up as a `TypeInitializationException` (`Patched/ImportResolver.cs:93-99`) — add `docs/game-guide.md` (about 80 lines) and link it from the root README; move "Conventions the game code follows" out of `samples/HelloMesh/README.md:91` into it.
- [severity: high] tools/build-shaders.mjs:27, tools/README.md:31,78, docs/architecture.md:88 vs src/Brutal.Vulkan.WebGpu/Profile.cs:57 — The ICD (and now the profile JSON and ICD README) advertise and accept 128-byte push constants, while the shader pipeline rejects blocks over 64 bytes and the architecture and tools documents say 64, so a game that trusts the device limit writes shaders that fail translation — raise `PUSH_MAX_BYTES` to 128 (the ring slot is 256 bytes) and fix the three statements, or lower the ICD to 64 and re-run `ProfileJsonSyncTests`.

- [severity: medium] README.md:6-24, tools/Shaders.Web.targets:34 — `dotnet test A B C` passes three projects, but VSTest `dotnet test` takes one project or solution (likely MSB1008; verify); the solution build runs `npm ci` in `tools/` from several browser projects in parallel and `tools/README.md:81` admits the race — use `dotnet test BrutalBrowser.slnx`, and add `cd tools && npm ci` to the quick start (or run the install once per solution build).

### src/Brutal.Vulkan.WebGpu (C# ICD and webgpu-glue.js)

- [severity: high] wwwroot/webgpu-glue.js:56,228-232 — More than 4096 push-constant updates in one submit reuse the last ring slot, so later draws read wrong constants; only a `reportError` is raised and no README mentions the limit — flush the ring and continue (or grow it) instead of reusing a slot, and document the number.
- [severity: medium] wwwroot/webgpu-glue.js:644, Icd.Queue.cs:95-107 — `device.lost` is only logged; `vkQueueSubmit` and `vkQueuePresentKHR` keep returning success, so a game never learns the device is gone — keep a `deviceLost` flag in the glue, return it with the replay result, and map it to `VK_ERROR_DEVICE_LOST` in `FinishSubmit` and `vkAcquireNextImageKHR`.
- [severity: medium] IcdLog.cs:53-64, Icd.Commands.cs:335-345 — `Ignored`/`Unsupported` concatenate the key and interpolate the message before the once-check, so every call to an ignored function (`vkCmdSetDepthBias`, `vkCmdSetStencilCompareMask`, `vkCmdSetViewport` with count > 1) allocates two strings; dynamic depth bias, the usual shadow-map call, is dropped after one warning — test the once-set with a `(function, reason)` key before formatting, and either implement dynamic depth bias (pipeline variants) or list it first in the known gaps.
- [severity: medium] Icd.Device.cs:134-142 — `vkDestroyDevice` releases only the queue; objects the app did not destroy keep their JS handles and WebGPU resources and nothing reports them — under `ValidateProfile` log the count and kinds from `HandleTable.LiveObjects()` at device and instance destroy.
- [severity: medium] Icd.Commands.cs:53,61 — `CommandBufferCountOffset = 28` reads BRUTAL's internal `VkCommandBufferAllocateInfo.CommandBufferCount` through a hard-coded offset — add a unit test on the field offset or expose the field in the loader patch.
- [severity: medium] WebIcd.cs:26, Bridge/WebGpuBridge.cs:9 — `WebGpuBridge` is a public abstract class whose members are all `internal abstract`, so nothing outside the assembly can subclass it, yet `WebIcd.Bridge` exposes it with a public setter — make both internal (the test project already has `InternalsVisibleTo`).
- [severity: medium] Registry.cs:81-300 vs Generated/StubTable.g.cs — The hand-written table repeats each command name three times (string, wrapper struct, method) and is edited separately from `Icd.*.cs`; the generated table still registers all 804 commands and is then overridden — have `tools/gen-icd-stubs.py` also emit the implemented table from the `vk*` methods of `Icd.*.cs` and skip stubs for them.
- [severity: medium] ShaderManifest.cs:106,122-173 vs tools/patch-wgsl.mjs:116-136 — WGSL bindings are reflected twice, with two regexes in two languages; the manifest `bindings` array (`build-shaders.mjs:145`) and `stage` are written but never read — either read `bindings` (add the comparison and read-only kinds to the manifest) and delete `Reflect`, or drop `bindings` from the manifest and architecture.md.
- [severity: low] Result codes and small hazards — `Icd.Pipelines.cs:109-111,631` returns `VK_ERROR_INVALID_SHADER_NV` for every pipeline failure (use `FEATURE_NOT_PRESENT` for unsupported state); `Icd.Pipelines.cs:156-157` indexes `stackalloc VkFormat[8]` without the clamp the dynamic-rendering path has; `Objects/HandleTable.cs:59-64` has an 11-bit generation and a LIFO free list, so an object created and destroyed every frame can alias a stale handle after about 34 s at 60 fps (use a FIFO free list); `Icd.Memory.cs:40-48` lets `AlignedAlloc` throw `OutOfMemoryException` across the ICD boundary (return `VK_ERROR_OUT_OF_HOST_MEMORY`); `Icd.Shaders.cs:15` casts `CodeSize` to `int` unchecked.
- [severity: low] Duplicated code — `Icd.RenderPasses.cs:197-273` (`vkCreateRenderPass` and `vkCreateRenderPass2` are 35 identical lines); `Icd.Pipelines.cs:178-201` vs `606-613` (used-group computation and `RefineFromShader` for graphics and compute) and `:453-454` (strip-index variants made with `string.Replace` on JSON); `Profile.cs:249,252` vs `Icd.Shaders.cs:85-89` (device id and cache UUID literals) — extract `BuildRenderPass`, `CollectGroups`, and two constants; carry the strip topology in a typed description instead of editing JSON text.
- [severity: low] Test seams in product code — `CommandStream.cs:140-165` (`ReplayStreamReader`), `Objects/SyncObjects.cs:89`, `IcdLog.cs:14,66`, `WebProfileLint.cs:14`, `Profile.cs:146`, `Icd.Descriptors.cs:605,624`, `Icd.Pipelines.cs:437`, `ShaderManifest.cs:62`, `Icd.Debug.cs:24`, and in `webgpu-glue.js:117-144,622-625,686` the `readPixel` hook with its own staging buffers plus a second frame counter — gather the C# seams in one `internal static class TestSupport`, and enable the JS hooks only with `init({ testHooks: true })`.
- [severity: low] Unverified or unexplained code — `ShaderHash.cs:12-96` carries 80 lines of hand-written SHA-256 for a platform path that may never run on browser-wasm (the e2e would log `INFO ... managed SHA-256` if it did; delete it if it does not); `FeatureNames.cs:1` says "Generated from BRUTAL's struct layouts" but no generator is in the repo; `Icd.Device.cs:49` assumes every feature struct is below 256 bytes — add the generator or reword, and a `Debug.Assert(size <= 256)`.
