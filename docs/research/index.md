# BRUTAL in the browser — research bundle

Open Knowledge Format (OKF v0.2) bundle produced on 2026-10-16 for the proof of concept that runs BRUTAL-based C# game code in a browser (WebAssembly + WebGPU). Every file below is a concept with YAML frontmatter (`type`, `sources`, `generated`, `status`); claims carry footnotes keyed to source ids. Everything is `status: draft` and machine-generated; nothing has been human-verified yet. Related: the implementation plans in `../../plans/` and the experiment projects in `../../projects/`.

Reading order for a new session: Overview → Decisions → Experiments → the area you need. The `references/` folder mirrors external material (NuGet registration metadata).

## Experiments

What was actually built and measured in `projects/exp-*` (exact commands, numbers, failures).

* [exp-01: BRUTAL on .NET 10 browser-wasm without wasm-tools (smoke test, function pointers, signature coverage, interop cost)](experiments/exp-01-dotnet-wasm-smoke.md) — Measured, in headless Chromium, what of the BRUTAL NuGet packages works on stock .NET 10 browser-wasm (Mono interpreter, no relink/AOT). Covers the exact Brutal.Platform and Brutal.Vulkan loader failures, NativeLibrary/DllImport behavior, whether a C# "managed ICD" can be reached through BRUTAL's delegate* unmanaged tables, which of BRUTAL's 45 wasm32 Vulkan call signatures are callable, JSImport heap access, and per-call costs. *(Experiment Report)*
* [exp-03: C# → WebGPU through [JSImport] on .NET 10 browser-wasm (spinning triangle and interop cost)](experiments/exp-03-webgpu-jsimport.md) — A prototype that drives WebGPU from C# through int handles, wasm-heap pointer reads, JSON pipeline descriptors and a batched binary command stream, verified in headless Edge/Chromium with pixel checks, with measured per-call, batching, pipeline-creation and queue round-trip costs that feed the Vulkan-on-WebGPU layer design. *(Experiment Report)*
* [exp-04: Brutal.Vulkan rebuilt from source with a pluggable loader (desktop MoltenVK, managed ICD, browser-wasm)](experiments/exp-04-brutal-vulkan-source-build.md) — Rebuilds BRUTAL's Brutal.Vulkan from the public source, adds a two-file pluggable-loader patch with no public API change, and shows it works on macOS/MoltenVK, with a C# vkGetInstanceProcAddr on desktop, and in headless Chrome on .NET 10 browser-wasm next to the unmodified NuGet Brutal.Vulkan.Abstractions. *(Experiment Report)*
* [exp-06: managed function-pointer flavor of Brutal.Vulkan + Abstractions (C# ICD called through delegate*<…> on desktop and browser-wasm)](experiments/exp-06-managed-fnptr-flavor.md) — Builds Brutal.Vulkan and Brutal.Vulkan.Abstractions from the read-only BRUTAL source with every delegate* unmanaged[Cdecl] rewritten to a managed delegate*, and shows that a plain-static-method C# Vulkan ICD then runs under BRUTAL's own bindings on CoreCLR and on .NET 10 browser-wasm (no wasm-tools, no UnmanagedCallersOnly, no JS trampolines), with all signature shapes intact, catchable ICD exceptions and ~31–41 ns per Vulkan call in the interpreter. *(Experiment Report)*
* [exp-07: Mono AOT (RunAOTCompilation) vs the interpreter for the HelloMesh browser build](experiments/exp-07-hellomesh-aot.md) — Measures a trimmed Release publish of samples/HelloMesh/HelloMesh.Browser with and without -p:RunAOTCompilation=true -p:WasmStripILAfterAOT=true on .NET 10 browser-wasm (publish time, _framework size raw and brotli, READY, FRAME 120, PERF avg/p95/max, e2e 17/17), and says when AOT is worth its cost for a game. *(Experiment Report)*
